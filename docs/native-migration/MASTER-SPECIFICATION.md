Berean Native Migration Master Specification
Implementation brief for Claude · 5 November 2026
Build Berean for macOS and iPhone with native Swift interfaces and a shared Swift core. Keep the existing apps releasable while building two parallel Dev apps. Start with the legacy behavior oracle, then prove the store, importer and sync engine against copies and isolated fixtures before shipping native write access. The migration succeeds when users can update in place or import through their supported distribution route, keep their data and workflows, and continue syncing while their other devices update on their own schedule.

3 Architecture and ownership
Use a single Xcode build graph with BereanMac and BereanIOS plus iOS Share and Widget targets, reusable Intents, and an isolated Mac Dev tooling target. Put local packages in Packages/BereanKit with dependency directions from platform composition to services, store and pure domain modules. Reserve AppKit and UIKit for platform UI. No Electron, React or Capacitor product runtime in the finished apps. An owner-approved isolated WebKit host can display external YouTube content. Core reader, notes, search and app navigation run natively.
Pure modules cover BereanDomain, BereanReference, BereanText, BereanNavigation and Markdown model/codec. Share immutable IDs, route intents, text offsets and formatting contracts. Audit JavaScript regex behavior and generate fixtures for ambiguous names, grouped references, ranges, Strong's, Hermas and Recognitions, and canonical URLs and filenames.
Put SQLite behind BereanSQLite and BereanStore. Prototype GRDB with the same SQL, WAL, per-connection foreign keys, bound parameters and FTS5 behavior. Keep raw SQLite as a fallback if required by test results. Verify platform SQLite versions and compile options rather than assuming FTS tokenizer equivalence. Keep corpus databases read-only and independent of the user store.
One serialized writer owns DB mutations. Capture sync outbox changes within the same transaction, including vault and import paths that represent local edits. Remote apply updates bookkeeping and invalidates UI without echoing changes. Emit typed change events after commit. Keep reads, search, indexing, journal IO and synthesis off the main actor. Use task cancellation, bounded queues and local redacted diagnostics.
BereanSync owns entity registry, HLC, hashing, merge, journal, snapshot, compaction and holds. Inject clock, filesystem and failure points. Implement transport per distribution route and test account/token behavior before sharing transport. Use TypeScript as a test oracle. The recommended default is a Swift sync engine once conformance passes. Require an explicit owner decision and removal gate for any temporary shipping JS engine.
BereanSpeech and BereanResearch share portable text preparation and contracts. Platform adapters handle audio, local models, secrets, spotlight, haptics, location, files, iCloud, printing and WebKit. The existing native SQLite, App Intents, Share and Widget code can supply proven pieces after removing Capacitor coupling. Use audit 02 and 14 to map Electron IPC and iOS plugin callers to service APIs, platform adapters or documented retirements.
4 Migration stages and required evidence
Stage 0 Stabilize the oracle and rehearse isolation
Pin the legacy app to the corrected baseline. Reproduce builds and smoke checks in a clean Dev worktree. Make Swift simulator compile and tests part of CI alongside legacy checks. Replace the no-op vault integration test with a real temp-vault harness. Create deterministic exporters for hash, op, merge, reference, Markdown, offsets, text and speech goldens. Fill audit 11 gaps in historical DB, PDF metadata and Study Trail fixtures. Resolve the localStorage field inventory, sync registry count discrepancy and write-path census. Reproduce D5–D7, establish fixes and ship or schedule the legacy bridge before mixed native writes.
Gate: reproducible outputs tied to exact SHAs, goldens after PRs #9–11, no Dev/production identity crossing, and legacy regression evidence. Run the performance baseline suite before setting budgets.
Stage 1 Pure Swift parity and high risk prototypes
Port reference parsing, display tokenization, search preparation, routes and Markdown AST/codec, then speech chunking and alignment. Build two native Dev shells with read-only corpus data while prototyping TextKit reader, note tables and iPhone gesture arbitration. Run shared tests on Mac and iOS simulator. Use JavaScript UTF-16 offset semantics explicitly and map raw source spans to displayed spans through substitutions, annotations, grapheme clusters and bidi. Preserve IDs, line endings and normalization exactly on persisted text. Re-anchor existing highlights only through an explicit tested policy.
Gate: 100% golden parity, seeded Unicode and parser fuzz runs, display-map checks including Hebrew, Greek, combining marks, surrogate pairs and word replacer rules. Verify the highlight corpus on authorized copies before enabling any highlight writes. Confirm reader frame and memory budgets on Psalm 119, long scroll and 0/50/500 highlights.
Stage 2 Store and schema compatibility
Port schema and SQL from the existing migration and service code. Exercise v43, v47, v48 and v49 fixtures plus newer, corrupt and low-space cases. Preserve version 18 gap handling through the existing version semantics. Compare normalized sqlite_master, table and trigger definitions, foreign keys, search result sets and ordering. Open all 26 bundled databases read-only on both platforms. Refuse unknown newer schema and fail closed if pre-migration backup cannot be made. Check transaction rollback, WAL snapshots, FTS tokenization, mixed column storage, cascades and crash behavior. Run against candidate minimum OSes.
Gate: verified schema and data parity, integrity and FK checks, FTS parity, repeatable migration and backup failure behavior. Keep v48 production and v49 development distinct. Plan the legacy v49 deployment as a coordinated compatibility event across platforms. A v48 reader stops pulling from a v49 publisher until updated. Freeze on the verified production compatibility level for native rollout.
Stage 3 Sync conformance and adversarial testing
Run audit 11 Stage A deterministic protocol comparisons, Stage B multi-client simulated filesystem and Stage C real Mac/iPhone in the Dev container. Compare fields, record versions, clocks, failures, conflicts and convergence against the legacy client. Include fresh, mixed and all-native populations. Keep production sync physically inaccessible to Dev builds.
Gate: exact hash/codec/merge parity, zero unexplained differences across replay and seeded scenarios, D1–D4 regression checks and documented resolution of D5–D7 before production. Exercise real dataless downloads, large snapshots, offline recovery and account changes. Save evidence from both mixed directions, Electron Mac plus native iPhone and native Mac plus Capacitor iPhone.
Stage 4 Bridge release and importer
Ship a legacy bridge through the normal release process after owner approval. Map every Berean localStorage key to SQLite, preferences or an explicit legacy export field. Export a versioned JSON sidecar and Mac full export bundle without secrets. Confirm skipped-bridge upgrades through a signed storage-recovery prototype or a documented recovery flow. Build channel-specific first run with dry run, source selection, verification report, safe activation and recovery UI. Rehearse rollbacks on every supported route with sync off and pending edits.
Gate: successful production-sized fixture import and restore, failure injection at every checkpoint, repeatable upgrade without duplicates, and real interaction tests for each signed identity route. Open separately migrated copies before any eligible production adoption.

6 Sync coexistence contract
Keep the iCloud Documents journal and current wire contract. Preserve the device directory layout, version, entity keys, IDs, op ordering, exact field hashes, HLCs, snapshot format, acknowledgments, conflicts, holds and tombstone semantics. Preserve ownership and deterministic IDs, including sunrise-aware daily note identity. Trash is a live record state until a genuine purge. Keep new entity types, JSON shapes and schema changes out of mixed releases. Derive canonical kinds from the registry and explicitly cover study profiles and saved research invalidation.
D1 — Acknowledge/delete only the outbox version actually published. Test an edit during push and a crash between publication and acknowledgement.
D2 — Apply dependency retries until no progress and hold unresolved records. Confirm snapshot bootstrap preserves tag edges and produces correct counts.
D3 — Cap acknowledgement before the earliest parked op. Test unknown kinds, malformed records, FK failures and pruning pressure. Never lose failed payloads needed for retry.
D4 — Capture every synced local mutation transactionally. Test external vault writes, imports and trash/purge paths with real vault files.
D5 — Stale external files can carry newer mtime. Require tested content/version-based conflict handling, an atomic write and preserved conflict copy. Set one active vault writer and document external edits.
D6 — Test immediate invalidation of study profiles and saved contexts after remote apply, including already-open views.
D7 — Compare account and container before writes on both platforms, hold on mismatch or unavailable identity, and rehearse sign-out and return. Validate iPhone token stability across launches and updates. Verify restore/fork behavior beyond relying on birthtime.
Run concurrent edits, offline branches, more than 64 lineage updates, clock skew, reordered ops, delete versus edit, bulk purges, huge notes, thousands of journals, malformed inputs, dataless files, interrupted downloads and termination during each engine phase. Include a 90-day silent device returning and a publisher with empty outbox whose files have yet to upload. Validate empty bootstrap never emits mass deletes. Prove convergence through digests of entity/key/HLC/hash, independent from displayed sync status.
Controlled rollout
1. Dev only under iCloud.com.berean.app.dev. Verify signed identifiers, effective entitlements and profile, path separation, sync gate defaults, URL and app group routing.
2. With separate authorization, read-only production shadow against a verified copy. Apply only to that copy and enforce transport write prohibition, including manifests, acknowledgments, snapshots and pruning. Compare daily digests with the current app. Stop on unexplained variance.
3. Pilot one production writer with a new device ID and frozen schema after shadow passes. Any copied DMG database or restored/forked instance needs a distinct identity and the verified legacy ownership republish path. An in-place iPhone or MAS upgrade can retain identity only with proven single-writer continuity. Quiesce the retired writer and confirm its edits reached peers before handoff.
4. Keep mixed populations interoperable for at least the audit's 90-day silent window. Inhibit aggressive compaction and prune only with proof every relevant reader can recover. Monitor digest and count drift, failed ops, unreadable files, conflict trends and abnormal operation bursts. Halt writes and preserve store plus journal if any hold, unexplained loss or divergence appears. Set numerical budgets and burst thresholds from the rehearsed workload before pilot.
5. Roll back by pausing native writes and confirming published edits have reached compatible peers. Preserve unsent edits through verified export/recovery. During phased rollout, use a higher-version recovery build if needed. End coexistence only once known devices are current, acknowledgments agree, outboxes and holds are resolved, backups restore and the owner signs off. Keep journals and device directories. Schema evolution starts after a separate review.
